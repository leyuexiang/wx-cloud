# 物联网有界容量验收

`measure-capacity.py` 通过真实管理接口、消息队列遥测传输协议（MQTT）及认证长连接（WebSocket）验证接收和定向推送。配置参考 `capacity-config.example.json`，身份及代理密码只通过标准输入 JSON 提供，禁止写入仓库、命令参数或公开日志。

操作顺序为 `prepare`、`run`、`cleanup`，每步均指定 `--config`、`--state` 和 `--report`。本地报告和缓存使用 D 盘；使用独立连接器及代理，保留原场景与接收审计。清理前停止隔离接入；发生中断时依据资源清单及场景/连接器分页重新核对。

- 最大 1000 个逻辑设备、50 条连接、120 轮，每轮五秒；缺省仍为 12 轮（一分钟）。一个网关汇聚逻辑设备，不等于千条独立设备连接。
- `run --scope draft` 校验草稿范围。`run --scope publication` 要求资源清单含通过正式发布接口返回的 `publicationId`，该固定发布必须对应清单中的场景及修订。缺省复用管理身份，`distinctAccounts=1`；可在标准输入增加 `viewers` 数组，每项包含查看用户名和密码，不落盘。多账号按登录结果的服务端用户编号去重，不以票据数或用户名数代替独立身份数；夹具管理和票据签发仍用管理身份。
- 提供查看账号时，选取前 `--clients` 个，数量不足或重复立即失败；每条连接使用其自身登录会话，报告记录非秘密用户编号。结束时逐条注销查看会话、撤销票据；部分登录失败也保留已建立会话供清理。查看角色应仅含状态查询/订阅及所需的无动作祖先菜单，另行验证无账号管理/场景写权限。浏览器渲染容量仍独立验收。
- 固定发布票据有效期 1200 秒，每条连接各一张，只在进程内使用，结束后逐条撤销。`cleanup` 先读取发布状态、必要时撤销发布，再删除本轮绑定与场景；已经撤销后的重试可继续执行。
- 每 20 个点位分批订阅，25 秒续租。积压超过十秒、发送排程落后超过两秒或客户端发生错误即停止，最多再观察二十秒。不放宽保护来掩盖无效负载。
- 20 条 MQTT 消息在途，编号在 1～65535 间回绕，逐个核对确认；数值序号独立递增，不能随报文编号重置。
- 发布使用独立进程，与 50 路接收线程隔离；同机共享定长发送时钟数组，由发送进程单写、接收端只读。父进程每 100 毫秒检查客户端错误及十秒积压，通知发送进程停止；结束等待回执并关闭进程和管道。两秒排程保护仍由发送进程执行，不能通过延长门槛把无效负载算作成功。
- 固定发送时钟数组、字节位图与直方图验证逐条完整性和重复。统计载荷上界约 19 MB（1000×120×50），不代表整个进程的常驻内存。延迟以一毫秒向上取整，超过 60 秒的分位使用实际最大值保守报告。旧历史分位采用原精度，比较时注意统计方法。
- 完整收到全部消息、零重复/错误、延迟第 95 百分位不超过五秒才通过本工具的工程观察门槛；正式业务延迟指标另行签收。逐分钟样本是采样瞬间累计量，末尾在途帧以最终完整性为准，不能将采样差额直接计为丢失。

十分钟不代表长期稳定性；协议连接不代表浏览器、三维渲染或独立账号容量。负载发生器与浏览器同机时记录资源竞争及排程停止，保留失败轮，再独立复测。服务程序、连接配置、数据库持久性及证书变更应单独记录，不能用工具成功替代部署验证。

## 可选接收分进程

`run` 可增加 `--receiver-processes 5`，将 50 条连接分配给五个接收进程；允许 1～5 且不超过客户端数，缺省 0 保持原线程模式。使用系统的独立进程启动方式（spawn），不共享已经打开的套接字；所有进程合计最多五条连接同时准备，订阅分批、权限和逐帧范围检查不变。发送仍在独立进程，单调发送时钟、位图、直方图及统计计数使用固定共享缓冲，没有逐帧管道传输。

复制工具时须同时复制 `capacity_receivers.py`、`probe-mqtt.py`，使用当前 `websocket-client` 依赖；不能仅复制主脚本再把辅助模块缺失当成后台业务错误。身份和票据仅在内存启动参数中传给指定子进程，不写命令行或文件。异常类型只保留稳定枚举，不记录带令牌的连接地址。

报告增加 `receiverIsolation`、`receiverProcesses`、`receiverErrors`、`receiverCpuSeconds`、`receiverProcessCpuSeconds`、`parentCpuSeconds` 及 `cpuMeasurementWindow`。准备完成后全部子进程确认 CPU 计时起点才启动发布；累计 CPU 计入接收排空，包含父进程、发送进程和所有接收进程，不能拿单个父进程 CPU 冒充全部成本。正常与异常结束都必须取得最终回执、释放接收进程，缺回执/异常退出/清理超时均失败，票据和登录会话仍由父进程回收。

两模式在相同入口、账号及负载下交替对照并保留全部结果；一次分进程较快不能证明历史高延迟已归因。进程客户端也不是实际浏览器播放器。
