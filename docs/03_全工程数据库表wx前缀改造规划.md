# 03 全工程数据库表 wx 前缀改造规划

> 状态：分域实施中；盘点基于 2026-10-16 的仓库代码与建表脚本。

## 1. 目标与命名规则

项目自有物理表统一采用小写 `wx_` 前缀，例如 `system_user` 改为 `wx_system_user`；已有 `wx_` 前缀的表保持原名，不重复添加。Java 类名、接口路径、Kafka 主题、列名和索引名不因表名改造自动变更。达梦等大小写敏感数据库沿用其现有大写风格，目标名为 `WX_` 加原表名。

表名改造必须同时覆盖新环境建表脚本、实体映射、手写 SQL、迁移脚本、初始化数据、代码生成模板和部署配置。不能只修改建表脚本后直接启动服务。

## 2. 仓库盘点

从 SQL `CREATE TABLE` 和生产 Java `@TableName` 提取的表名共 **230** 个；其中 **225** 个尚无 `wx_` 前缀，**5** 个已符合。未加前缀的表中，**11** 个是 Quartz 调度器的 `qrtz_*` 框架表，其余 **214** 个是项目自有或项目随附的业务与测试建表定义。完整逐表映射见 [03 数据库表名 wx 前缀映射](./03_数据库表名wx前缀映射.csv)。这份清单是仓库静态盘点，实际数据库仍需在迁移前按库核对。

| 范围 | 主要来源 | 处理方式 |
|---|---|---|
| IoT 接入 | `wx-module-iot/db`、实体和 Inbox SQL | 三张现有表已改用 `wx_`；旧库使用原位改名脚本 |
| 三维、植被、二维 | `db/3d`、`db/vegetation`、`wx-module-2d/db`、对应实体/Mapper | 植被四张表已改用 `wx_`；三维和二维按实际数据库分别迁移 |
| 平台业务模块 | system、infra、bpm、pay、member、mall、crm、erp、ai、mp、report | 已完成 system/infra、bpm 与 member；其余模块按实际数据库分域同步更新 |
| 第三方框架 | Quartz `qrtz_*`；Flowable 运行时可能自动建表 | 先核实框架是否支持表前缀及历史数据迁移，再决定是否纳入；不得只改项目 SQL 快照 |

## 3. 已落地：IoT 表

| 旧表 | 新表 |
|---|---|
| `iot_connector` | `wx_iot_connector` |
| `iot_device_binding` | `wx_iot_device_binding` |
| `iot_message_inbox` | `wx_iot_message_inbox` |

新环境使用 `wx-module-iot/db/iot.sql`。已部署旧环境先执行历史 Inbox 字段迁移脚本，暂停 IoT 写入并备份，再执行 `wx-module-iot/db/iot-wx-table-prefix-migration.sql`，最后部署新服务。MySQL `RENAME TABLE` 保留原表数据；若目标表已存在，脚本失败以避免覆盖。历史迁移脚本保留原表名，作为旧版本迁移记录，不在改名后重复执行。

植被模块的 `veg_generation_task`、`veg_generation_tile`、`veg_publication`、`veg_publication_lock` 同步改为 `wx_veg_*`；新环境使用 `db/vegetation/vegetation.sql`，旧环境先完成原有字段迁移，再执行 `db/vegetation/vegetation-wx-table-prefix-migration.sql`。生产实体、发布锁 SQL、测试建表和两份植被设计文档已同步更新。

## 4. 已落地：system 与 infra 第一批

`db/system/9tyf-vue-pro.sql` 中的 43 张项目自有平台表已统一改为 `wx_system_*` 或 `wx_infra_*`，并同步更新生产实体 `@TableName`、Mapper 注解 SQL、统计查询、租户忽略表配置、代码生成 SQL 模板、测试建表和清理脚本。旧库执行 `db/system/system-infra-wx-table-prefix-migration.sql` 完成原位改名，数据、索引和约束由数据库保留；Quartz `qrtz_*` 表未纳入。

## 5. 已落地：BPM 流程域

8 张项目自有流程表已统一改为 `wx_bpm_*`，同步更新实体映射和测试建表、清理脚本。旧库执行 `wx-module-bpm/db/bpm-wx-table-prefix-migration.sql` 完成原位改名；Flowable 自动管理的 `ACT_*`、`FLW_*` 表继续保持原名。

## 6. 已落地：member 会员域

11 张会员生产实体表改为 `wx_member_*`，同步更新跨模块会员统计查询与测试 SQL。旧库迁移脚本位于 `wx-module-member/db/member-wx-table-prefix-migration.sql`。当前仓库没有这 11 张表的生产建表脚本，执行前必须按实际业务库核对源表与目标表；仅见于测试资源的 `member_brokerage_record` 已同步改名，但不列入生产迁移脚本。

## 7. 其余模块实施顺序

1. **核对实际库**：按数据库、模式（Schema）、表名和数据量核对映射清单；确认是否有未入库的第三方表、视图、触发器、外键与外部 SQL 作业。
2. **分域改代码**：先三维/植被/二维，再平台业务模块。每域同步修改新环境建表脚本、实体注解、Mapper XML/注解 SQL、初始化数据和代码生成配置。
3. **分域写迁移**：每个数据库单独提供前向改名脚本及冲突检查；保留已有历史迁移文件。大表改名安排维护窗口，避免元数据锁阻塞在线请求。
4. **切换服务**：暂停该域写入，备份并执行改名，校验表数量、行数及关键索引，再部署引用新表名的服务。旧版本服务不得与新表名服务混跑。
5. **回退与收尾**：失败时停止新版本，由单独的反向改名脚本恢复旧表名后回退服务；完成后更新运维 SQL、监控、数据同步和文档。

## 8. 发布门槛

- 每个域的数据库对象、代码引用和部署配置必须在同一发布计划中核对；未完成的域保留旧表名，不能提前修改运行映射。
- 迁移前确认目标表不存在、源表存在，备份可恢复，相关服务已停止写入。
- 迁移后检查实际表名、关键行数、索引、外键、租户隔离和主要读写链路；当前仓库静态检查不能代替数据库联调。
- 对 Quartz、Flowable 等框架管理表，必须先确认框架前缀配置与升级兼容性，再执行物理改名。
