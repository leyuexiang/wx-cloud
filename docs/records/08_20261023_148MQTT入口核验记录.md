# 2026-10-23 148 MQTT 入口核验记录

## 1. 核验范围

- 目标：`192.168.10.148`。
- 方式：TCP 端口探测，以及不带用户名/密码、不发布消息、不订阅主题的 MQTT 3.1.1 `CONNECT` 握手。
- 目的：确认是否存在可用消息代理（Broker）入口和认证策略；不尝试猜测凭据。

## 2. 端口结果

| 端口 | 结果 | 结论 |
|---:|---:|---|
| `1883` | 可达 | 存在 MQTT 明文入口 |
| `8883` | 不可达 | 当前未发现默认 TLS MQTT 入口 |
| `8083` / `8084` | 不可达 | 未发现常见 MQTT WebSocket 入口 |

## 3. MQTT 3.1.1 握手

### 随机客户端编号、无认证

返回：`20 02 00 02`，CONNACK 返回码 `2`，表示客户端标识被拒绝。

### 空客户端编号、无认证

返回：`20 02 00 05`，CONNACK 返回码 `5`，表示未授权。

这两次请求只建立协议握手，没有发布、订阅或写入业务消息；连接随后关闭。结果确认 Broker 正在监听 MQTT 3.1.1，并要求认证，同时具备客户端编号策略。没有凭据时不能继续验证主题 ACL、QoS 或设备报文。

## 4. 对 IoT 配置的影响

当前 IoT MQTT 默认要求 `ssl://`，普通 `tcp://` 必须显式开启 `IOT_MQTT_ALLOW_INSECURE`。148 目前只探测到 `1883` 明文入口，不能在生产配置中把它当作 TLS 端点；需要部署方提供 TLS 端口和证书链，或明确授权开发环境使用明文并限制网络范围。

连接测试接口已具备临时清洁会话和 QoS 1 订阅确认，但要对 148 执行真实测试，还需要：

1. MQTT 用户名和密码或密钥服务引用；
2. 允许该账号连接的客户端编号规则；
3. 至少一个确切主题的订阅 ACL；
4. 若使用 TLS，TLS 端口、证书链和主机名匹配信息。

## 5. 当前结论

148 的 MQTT Broker 入口已从“未发现”更新为“`1883` 可达、需要认证”；真实 MQTT 上行仍未验收。禁止把匿名握手成功或端口可达写成设备接入成功，也不要为绕过认证把生产配置切换到明文。
