# 00 数字孪生平台全栈改造路线图

> 文档状态：整体设计规划与实施进度持续更新
>
> 适用范围：数字孪生、物联网接入、规则判断、业务流程、三维展示和运营管理
>
> 当前阶段：阶段二物联网接入最小闭环，已完成连接器、设备绑定和统一遥测事件基础能力

## 1. 规划结论

平台采用“事件驱动的数字孪生底座 + 规则引擎 + 流程引擎 + 三维表现层”的演进路线。改造以业务闭环为单位逐步交付：

```text
外部物联网服务/设备
        │ MQTT、HTTPS、平台 API、边缘协议适配
        ▼
物联网接入服务（IoT Gateway）
        │ 设备身份、协议转换、数据点映射、连接健康
        ▼
规范化事件总线（Canonical Event Bus）
        │ Kafka：twin.event.v1
        ├──────────────► 规则服务（Rule Service）
        │                         │ 事件匹配、窗口、去重、告警
        │                         ▼
        │                   事件/告警（Incident）
        │                         │ 需要人工处理或长事务
        │                         ▼
        │                   流程服务（Workflow）
        │                         │ 审批、派单、计时、补偿、升级
        │                         ▼
        └──────────────► 数字孪生服务（Digital Twin）
                                  │ 状态投影、设备绑定、场景对象
                                  ▼
                        三维端/管理端/运营端

流程动作 ──► 命令网关 ──► 物联网接入服务 ──► 外部设备/平台
                  ▲                 │
                  └─ 接收确认/执行确认 ─┘
```

改造顺序遵循以下原则：

1. 先定义跨服务数据契约，再开发服务和页面。
2. 先打通一个端到端业务闭环，再扩充协议和行业能力。
3. 新链路与旧链路并行运行，通过开关、租户、场景和设备范围逐步切换。
4. 现有 Flowable 作为统一流程引擎，平台不再引入第二套流程运行时。
5. 外部物联网服务只通过物联网接入边界进入平台，不直接访问内部 Kafka、数据库或三维服务。
6. 三维端负责展示和交互，规则判断、权限校验、命令生命周期和流程状态由服务端负责。

## 2. 当前系统基线

### 2.1 后端基线

- 根工程是 Java 17、Spring Boot 3.1.x 的 Maven 多模块工程。
- `wx-module-3d` 已经承担 Kafka 消费、Redis 最新状态、消息持久化和 WebSocket 推送，是现有三维实时数据入口。
- `wx-module-bpm` 已经集成 Flowable，具备按流程定义启动流程实例的能力。
- 现有业务消息和任务消息存在多类主题与消费者，历史数据模型、设备消息和预警展示模型耦合较多。
- Kafka、Redis、WebSocket 已具备基础设施条件，但事件命名、版本、幂等和失败重放需要统一。
- 场景、模型、设备绑定和版本化持久化已经有重构方向，应采用增量投影方式与物联网改造衔接。

### 2.2 前端基线

- `Web/wx-web-2.0` 是 React、Umi Max 管理端，包含场景管理、资源管理、场景预览和后台 API 生成入口。
- `Web/web-unity` 是 Vue 3、TypeScript、Three.js/Cesium、Pinia 的三维编辑器和预览端，已有 WebSocket 和场景数据配置规范。
- `Web/wx-communication-outter` 当前主要解决 iframe 外部通信和页面集成，不具备物联网协议接入职责。
- 前端应沿用现有两个技术栈，通过统一 API 契约、事件字段和权限模型协作，不安排框架重写。

## 3. 目标分层与服务职责

### 3.1 物联网接入服务（IoT Gateway）

建议新增 `wx-module-iot`，职责限定为外部连接和设备数据边界：

- 管理 MQTT、HTTPS、第三方物联网平台 API 等连接器。
- 保存连接配置、认证引用、连接状态、重连次数和最后心跳。
- 管理外部设备标识、内部设备标识、数据点标识和单位映射。
- 将外部数据转换为规范化遥测事件，发布到 `twin.event.v1`。
- 接收 `twin.command.v1`，执行下行命令并发布 `twin.command.ack.v1`。
- 区分传输层接收确认和设备执行确认，记录完整命令审计。
- 对外部平台抖动、断线、限流和重复投递做隔离。

物联网服务不承担规则判断、业务审批、三维渲染和任意脚本执行。

### 3.2 规范化事件总线（Canonical Event Bus）

统一事件最小字段：

```json
{
  "eventId": "事件唯一标识",
  "eventType": "telemetry|status|alarm|command_ack",
  "schemaVersion": 1,
  "tenantId": "租户标识",
  "source": { "connectorId": "连接器", "protocol": "mqtt" },
  "device": { "deviceId": "内部设备", "externalId": "外部设备" },
  "point": { "pointId": "温度", "value": 26.4, "unit": "°C" },
  "occurredAt": "设备发生时间",
  "receivedAt": "平台接收时间",
  "traceId": "全链路追踪标识",
  "quality": "good|uncertain|bad",
  "payload": {}
}
```

事件必须可追踪、可去重、可重放。时间序列数据、最新状态和业务事件采用不同的保留策略，避免所有数据都进入同一张业务表。

### 3.3 规则服务（Rule Service）

建议新增 `wx-module-rule`，一期采用数据库持久化的 JSON 规则定义和轻量执行器：

- 规则草稿、版本、发布、停用和回滚。
- 设备、点位、场景、租户和事件类型筛选。
- 阈值、变化率、连续次数、时间窗口和组合条件。
- 冷却时间、去重键、优先级和告警升级。
- 试运行、历史回放和命中解释。
- 产生事件/告警（Incident），再由策略决定是否启动流程。
- 通过事务发件箱（Transactional Outbox）发送告警和流程启动请求。

规则服务不直接控制设备。需要控制设备时，生成受权限和审批约束的命令意图，由流程或命令网关继续处理。

### 3.4 流程服务（Workflow）

复用现有 `wx-module-bpm` 的 Flowable 能力，扩展统一业务接口：

- 以 `incidentId`、`businessKey` 和规则版本建立关联。
- 支持人工确认、派单、审批、超时升级、补偿和撤销。
- 流程动作调用命令网关，流程实例保存命令状态，不直接连接设备。
- 启动、重试、回调、取消均要求幂等。
- 对流程定义、版本、权限和操作记录统一审计。

单条遥测事件不应启动流程；只有形成业务事件且命中流程策略时才启动流程。

### 3.5 数字孪生服务（Digital Twin）

现有 `wx-module-3d` 保留场景和三维表现职责，逐步演进为数字孪生状态服务：

- 维护设备与场景对象的绑定关系。
- 消费规范化事件，更新 Redis 最新状态和查询投影。
- 通过 WebSocket 向三维端推送状态、告警和流程摘要。
- 为历史查询和场景回放提供只读 API。
- 兼容旧 Kafka 消息，采用适配消费者逐步迁移旧业务消费者。
- 在场景版本化重构完成前，支持旧工程 ID 和新场景版本 ID 双向映射。

## 4. 核心业务闭环

以“设备温度连续超限，审批后执行降载”为首个验证场景：

1. 外部设备或物联网平台发送温度数据。
2. 物联网接入服务完成认证、映射、单位校验和事件去重。
3. 接入服务发布规范化遥测事件。
4. 数字孪生服务更新设备状态，并推送三维对象颜色、数值和质量状态。
5. 规则服务按点位和时间窗口判断连续超限。
6. 规则服务创建一个可去重的事件/告警，并记录命中规则版本和条件解释。
7. 流程服务按策略创建处理流程，进入人工确认或审批节点。
8. 审批通过后，流程服务生成带幂等键和过期时间的命令。
9. 命令网关校验租户、用户、设备和动作权限，发布下行命令。
10. 物联网接入服务向外部平台或设备发送命令，记录传输接收确认。
11. 设备执行后回传执行确认，平台更新命令状态、流程节点和三维对象状态。
12. 超时、失败或重复执行进入重试、补偿、人工介入和审计链路。

## 5. 全栈改造边界

### 5.1 管理端：`wx-web-2.0`

新增管理能力，页面按业务对象组织：

- 连接器管理：协议、地址、认证引用、启停、连接健康。
- 设备和点位管理：外部 ID、内部 ID、数据点、单位、质量和绑定场景。
- 规则管理：草稿、条件编排、版本发布、试运行、回放和命中解释。
- 事件/告警中心：状态、优先级、负责人、处理时限和关联流程。
- 流程监控：实例、节点、命令、超时、失败和补偿。
- 运维观测：事件积压、死信、连接断线、命令延迟、规则耗时和接口错误。

管理端只编排和展示规则及流程元数据，最终校验由后端执行。

### 5.2 三维端：`web-unity`

增加与空间关系有关的能力：

- 设备绑定、解绑和绑定校验。
- 设备状态、点位值、数据质量和更新时间。
- 告警对象定位、闪烁/颜色/图标状态和详情面板。
- 从三维对象打开告警、流程和设备历史。
- 在权限允许时发起人工动作，并显示命令状态和执行确认。
- 通过统一 WebSocket 事件模型接收增量状态，避免页面自行判断规则。

三维渲染、资源加载和编辑器状态继续使用现有实现，物联网数据通过 API 和 WebSocket 契约接入。

### 5.3 接口和类型

建议建立独立的契约目录，包含：

- REST API OpenAPI 定义。
- Kafka 事件和命令 JSON Schema。
- WebSocket 事件类型和版本。
- 错误码、权限码、状态枚举和分页约定。
- 前端生成类型和后端契约检查。

所有跨服务对象带 `schemaVersion`，字段新增保持向后兼容，破坏性变化使用新版本主题或新版本接口。

## 6. 分阶段改造路线

### 阶段 0：现状盘点和契约冻结

**目标**：明确边界，控制后续返工。

**工作项**：

- 梳理现有 Kafka 主题、消费者组、消息结构和数据库写入方。
- 盘点设备、点位、场景对象、旧工程 ID 和租户权限模型。
- 明确首个试点场景、外部物联网平台和协议。
- 输出事件、命令、告警、流程、WebSocket 五类契约草案。
- 建立兼容策略、数据保留策略、追踪字段和错误码。

**阶段门槛**：首个试点的设备范围、动作范围、验收指标和回滚开关确定；跨服务契约经评审后冻结第一版。

### 阶段 1：事件骨架和旧链路适配

**目标**：让新契约可以接入现有系统，并保持旧功能运行。

**工作项**：

- 建立 `twin.event.v1`、`twin.command.v1`、`twin.command.ack.v1` 主题规范。
- 增加旧消息到规范化事件的适配消费者。
- 引入事件唯一键、消费幂等、失败重试、死信和重放工具。
- 在数字孪生服务中增加规范化事件投影，同时保留旧消费者。
- 增加 traceId、事件延迟、积压、重复和丢弃指标。

**阶段门槛**：新旧链路对同一批事件的数量、设备状态和延迟可比对；异常事件可以定位、重放和回滚。

### 阶段 2：物联网接入最小闭环

**目标**：接通一个真实外部平台或协议，完成“采集到三维展示”。

**工作项**：

- 新增物联网接入服务和连接器抽象。
- 首期只实现已经确定的一个平台协议，建议从 MQTT 或 HTTPS 平台 API 选择。
- 完成连接配置、凭据引用、设备发现/导入、点位映射、在线状态和限流。
- 将数据发布为规范化事件，三维端显示数值、更新时间和质量。
- 以租户、场景或设备组作为灰度开关。

**阶段门槛**：连续运行、断线恢复、重复投递、非法数据、权限拒绝和连接器停用均有可观测结果；试点场景能回滚到旧数据链路。

### 阶段 3：规则只读闭环

**目标**：先验证规则正确性和可解释性，再引入自动控制。

**工作项**：

- 实现规则版本、发布、停用、冷却、窗口和去重。
- 支持实时命中、历史回放和试运行。
- 生成事件/告警，显示命中条件、原始数据和规则版本。
- 管理端提供规则编排和命中解释。
- 三维端关联告警对象和空间位置。

**阶段门槛**：规则结果可复现；同一事件不会重复创建业务告警；规则运行错误不会阻塞事件接入。

### 阶段 4：流程和事件处置闭环

**目标**：把告警变成可追踪的业务处置。

**工作项**：

- 扩展 Flowable 启动、回调、取消和重试接口。
- 建立事件/告警到流程实例的唯一关联。
- 增加人工确认、审批、派单、超时升级和补偿节点。
- 管理端展示流程节点和处理时限，三维端显示处置状态。
- 使用事务发件箱保证告警创建和流程启动请求的一致性。

**阶段门槛**：流程重复启动可收敛；流程异常可重试；告警、流程、操作人和规则版本可审计。

### 阶段 5：受控命令和闭环控制

**目标**：在明确权限和风险范围内执行一个低风险设备动作。

**工作项**：

- 建立命令网关、动作白名单、租户/角色/设备权限和审批策略。
- 设计命令幂等键、过期时间、重试上限、熔断和人工取消。
- 区分传输接收确认、设备执行确认和最终业务结果。
- 首期仅开放一个低风险命令，完成灰度和审计。
- 规则自动动作默认关闭，由流程策略显式开启。

**阶段门槛**：重复请求不会造成重复危险动作；设备无响应、执行失败和平台断线均能收敛到明确状态。

### 阶段 6：场景和设备模型增量升级

**目标**：让 IoT、规则、流程与版本化场景模型长期一致。

**工作项**：

- 将设备绑定从旧工程配置逐步迁移到场景版本投影。
- 为绑定关系增加生效版本、历史、来源和校验状态。
- 发布场景时生成设备和规则可见性快照。
- 对旧工程提供只读兼容投影，完成调用方迁移后再退役旧字段。

**阶段门槛**：场景发布、回滚、设备绑定和告警定位在不同版本下结果可解释；旧场景仍能访问历史数据。

### 阶段 7：规模化和能力增强

**目标**：根据真实指标决定是否引入更复杂的流计算和更多协议。

**工作项**：

- 按吞吐、规则复杂度和窗口长度评估流处理组件。
- 引入时间序列存储、冷热分层、归档和查询限流。
- 增加 OPC UA、Modbus、工业网关等协议时，优先采用边缘代理隔离现场网络。
- 建立连接器插件、协议认证、数据质量和兼容性测试矩阵。
- 逐步关闭已迁移的旧 Kafka 消费者和旧数据写入路径。

## 7. 数据和可靠性设计

### 7.1 标识和幂等

- `eventId` 标识单次事件，`deviceId + pointId + occurredAt` 用于业务去重辅助。
- `commandId` 标识命令，`idempotencyKey` 防止重复执行。
- `incidentId` 标识业务事件，规则版本和流程实例必须可追溯。
- 消费者使用 Inbox 或等价去重表；生产者使用事务发件箱。

### 7.2 状态分层

- 最新设备状态：Redis 或等价低延迟投影。
- 设备历史遥测：时间序列或分析存储，按保留周期归档。
- 业务事件、告警、流程和操作审计：关系数据库。
- 原始外部报文：按敏感级别和排障周期受控留存。

### 7.3 失败处理

- 可重试错误采用指数退避和上限。
- 不可解析、契约不兼容和权限错误进入死信队列。
- 死信必须记录原因、原始事件引用和处理人。
- 重放需要权限、范围、时间窗口和审计，禁止直接全量重放生产命令。
- 外部连接器使用断路器、并发限制和连接级别隔离。

## 8. 安全、权限和运维

- 认证信息只保存密钥引用，页面和日志不展示明文。
- 按租户、项目、场景、设备、点位和动作划分权限。
- 规则、流程和命令均经过服务端权限校验。
- 外部物联网平台使用出站连接；入站回调进行签名、时间窗和重放校验。
- 关键动作记录操作者、审批人、规则版本、流程实例、命令参数摘要和设备确认。
- 观测指标至少覆盖：连接在线率、事件接入量、事件延迟、重复率、规则耗时、告警创建耗时、流程启动耗时、命令成功率、设备执行延迟、死信数量和 WebSocket 推送积压。

## 9. 改造期间的兼容和回滚

采用“新增、旁路、比对、灰度、切换、清理”的迁移顺序：

1. 新增契约和适配层，保留旧主题、表和消费者。
2. 新链路旁路消费，暂不改变旧业务结果。
3. 对比新旧状态、事件数量和延迟，定位差异。
4. 按租户、场景或设备灰度启用新投影和新页面。
5. 逐步切换读路径，再切换规则和流程入口。
6. 最后迁移命令写路径和旧消费者，完成后再清理旧结构。

回滚通过功能开关、消费者组停用、投影回退和命令动作关闭实现。数据库迁移采用向前兼容的新增字段和新增表，旧调用方仍可运行后再进行删除操作。

## 13. yudao-cloud 参考评估

### 13.1 版本基线

本项目当前使用 Java 17 编译，当前本机运行时为 Microsoft OpenJDK 17.0.18 LTS。参考 `yudao-cloud` 时选择 `master-jdk17` 分支作为代码阅读基线；其该分支使用 Java 17 和 Spring Boot 3.5.x。`yudao-cloud` 默认 `master` 分支属于 JDK 8 和 Spring Boot 2.7 体系，不作为本项目依赖版本基线。

本项目暂时保持现有 Spring Boot 3.1.x 和依赖管理版本，另行制定框架升级计划后再评估向 Spring Boot 3.5.x 对齐，避免 IoT 功能开发和基础框架升级同时改变运行时行为。

### 13.2 可复用的结构

`yudao-module-iot` 采用 API、Core、Server、Gateway 四层模块：

- API：对其他业务模块暴露设备查询、命令和事件接口。
- Core：提供设备消息模型和消息总线抽象。
- Server：实现产品、设备、协议、告警和管理 API。
- Gateway：负责设备消息的解码、编码、协议连接和上下行通信。

我们的物联网服务可以参考此结构，落为 `wx-module-iot-api`、`wx-module-iot-core`、`wx-module-iot-server` 和 `wx-module-iot-gateway`。三维状态投影、规则判断和流程处置继续放在本项目自己的数字孪生、规则和 BPM 边界内。

### 13.3 可以借鉴的能力

- 设备、产品、物模型、数据点、设备分组和连接配置的管理模型。
- API 与实现分离，降低 IoT 模块对业务模块的依赖。
- 消息总线可插拔设计；本项目首期固定使用 Kafka，保留消息总线接口以便后续扩展。
- 网关层的协议编解码、上行设备消息和下行命令通道。
- 告警配置、告警记录、数据流转规则、场景联动和 OTA 等功能的目录组织方式。
- 多租户、权限、Redis、MyBatis、定时任务和 WebSocket 等通用工程模式。

### 13.4 必须重写或适配的部分

- 外部物联网平台适配：增加本项目的 MQTT、HTTPS、第三方平台 API 和回调签名适配器。
- 规范化事件：转换为本项目的 `twin.event.v1`，保留 `tenantId`、`sceneId`、`objectId`、`traceId` 和 `schemaVersion`。
- 设备绑定：增加设备、点位与场景对象之间的版本化绑定关系。
- 规则结果：从告警或场景联动结果转换为本项目的事件/告警（Incident），再决定是否启动 Flowable 流程。
- 下行命令：经过本项目命令网关、权限、审批、幂等和执行确认后才发送设备。
- 三维推送：将设备状态、告警和流程摘要投影到 Redis，并通过 `web-unity` 的 WebSocket 契约推送。

### 13.5 不建议直接复制的部分

- 不直接复制整个 `yudao-cloud` 父工程、依赖清单和 Spring Cloud Alibaba 部署体系。
- 不把其消息总线、RocketMQ、Redis Stream、Kafka 等多个选项一次性全部引入。
- 不把其后台 IoT 页面直接替换现有管理端和 `web-unity` 三维端。
- 不把场景联动规则当作本项目完整规则引擎；规则版本、历史回放、告警解释和 Flowable 关联需要独立设计。
- 不让 IoT Gateway 直接写三维表、规则表或流程表，统一通过规范化事件和命令契约协作。

### 13.6 推荐落地方式

第一步只参考其模块边界，创建本项目 IoT 的 API/Core/Server/Gateway 骨架；第二步实现一个外部平台或 MQTT 连接器；第三步把上行数据发布到 Kafka 并接入现有三维状态投影；第四步接入规则服务和 Flowable；最后再按现场协议需要扩展 Modbus、CoAP 或 OPC UA 边缘网关。
