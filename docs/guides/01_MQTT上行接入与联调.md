# MQTT 上行接入设计与联调

日期：2026-10-19。范围：外部设备/平台通过消息队列遥测传输协议（MQTT）上报到 IoT 服务；服务到三维可独立采用 WebSocket 或 MQTT。

本文记录已经实现的单连接运行模式。下一阶段的动态发现、多会话、配置版本和凭据演进见[05_IoT动态多连接接入方案与里程碑](../design/05_IoT动态多连接接入方案.md)，当前服务尚未实现该增量。

## 首版实现约束

首版提供 MQTT 3.1.1 通用 JSON 适配器，采用至少一次传输（QoS 1）。单个工作进程通过部署配置指定一个租户和连接器，连接器、设备绑定和点位映射沿用数据库管理。多连接器按独立工作进程部署；同一租户与连接器通过 Redis 有时限租约协调活动实例，避免重复长连接。功能默认关闭。

连接地址及凭据引用来自 MQTT 连接器。凭据引用指向 `IOT_MQTT_` 前缀的环境变量，内容为 `{"username":"...","password":"..."}`，不在数据库或日志保存密码。默认仅允许 `ssl://主机:端口`，校验服务器证书和主机名；自签名证书通过 JVM 信任库配置。开发环境可显式允许 `tcp://`。不允许地址嵌入用户名密码、路径、查询参数或任意协议。

连接器 `configJson` 采用 `{"topics":["pilot/device/telemetry"],"qos":1}`。首版仅允许 1 至 32 个确切主题，不启用通配订阅、厂商动态脚本或下行命令。客户端标识由租户、连接器和配置指纹确定，配置变化时使用新会话，防止旧持久订阅继续接收已移除主题。旧会话由 Broker 管理员清理或按 Broker 会话策略过期。

启用持久会话（`cleanSession=false`）和手动确认。报文通过校验并进入数据库接收记录（Inbox）后才发送 MQTT 确认；确认表示平台持久接收，不表示 Kafka 已发布或设备业务已处理。Kafka 异步失败仍保留在 Inbox，继续使用现有失败查询和人工重放；Broker 必须为发布方配置 QoS 1、持久存储与合适的离线队列上限。

每次接收均使用工作进程指定租户查询当前连接器，校验启用状态和配置指纹；报文不能指定其他租户、连接器或内部设备身份。MQTT 回调恢复外层线程租户上下文，复用现有点位换算、去重、抢占和发布链路。要求存在启用的设备绑定。

无效报文、数据库故障和租约失效时不确认消息，连接关闭后采用有上限的指数退避重连。无效报文可能形成阻塞，需要修复平台报文/绑定或由运维隔离 Broker 队列；首版不静默丢弃，也不假定日志等于可靠隔离。没有实际平台契约时不猜测厂商字段。

MQTT 协议版本暂固定为 3.1.1；MQTT 5.0 的原因码、会话过期和共享订阅作为下一阶段能力，不将“支持 MQTT”解释为支持所有版本或厂商协议。TLS 使用 JVM 系统信任链，当前未提供管理端上传客户端证书或双向 TLS 配置。

## 通用上报格式

每条消息表示一个点位，UTF-8 JSON，最大 64 KiB。`eventTime` 使用 ISO 8601 时间字符串；`traceId` 由来源提供并在重试时保持不变。同一事件的时间、点位、值和追踪号重试时不得变化。

```json
{
  "externalDeviceId": "sensor-001",
  "pointCode": "temperature",
  "value": 26.125,
  "valueType": "NUMBER",
  "unit": "°C",
  "quality": "GOOD",
  "eventTime": "2026-10-19T02:00:00.123456789Z",
  "traceId": "sensor-001-seq-1001"
}
```

客户端认证及主题访问控制由 Broker 执行；同一个连接器的主题只应允许其管理范围内的设备或平台发布。统一事件进入 `twin.event.v1` 后由三维投影和规则消费者分别处理；三维前端的通信协议不改变本适配器。

## 生命周期与故障边界

工作线程定期检查连接器，启用后建立连接，停用、删除、配置变化或租约丢失时释放连接。连接失败采用带随机抖动的指数退避，最长五分钟；连续稳定连接一分钟后才重置故障计数，避免毒消息导致快速重连。生命周期资源在应用停止时释放，不使用无限本地消息队列或重复创建线程池。

租约有截止时间，回调在截止时间后拒绝接收与确认；定时续租必须比较随机令牌，旧实例不得续租或删除新实例租约。正常无阻塞情况下，每五秒检查连接器；数据库或网络阻塞会延长检查间隔，每条报文还会重新检查连接器。停用检查与消息入库之间没有跨系统事务，已进入处理的报文可能完成持久接收。尚未完成真实 Broker、数据库和网络故障联调前，不宣称生产验收完成。

## 配置与启用顺序

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `IOT_MQTT_ENABLED` | `false` | 创建 MQTT 工作进程的开关 |
| `IOT_MQTT_TENANT_ID` | 空 | 必须为已启用的有效租户 |
| `IOT_MQTT_CONNECTOR_ID` | 空 | 租户内 MQTT 连接器的业务编号 |
| `IOT_MQTT_ALLOW_INSECURE` | `false` | 仅本地联调时允许 `tcp://` |
| 连接器的 `credentialRef` 指向的变量 | 无 | `IOT_MQTT_...` 名称，JSON 用户名密码 |

1. 在 Broker 准备应用账号、允许订阅的确切主题、QoS 1 与持久会话；同时配置持久化、离线队列容量、报文大小上限及会话清理策略。适配器限制业务载荷 64 KiB；Paho 在回调前已经读取网络帧，因此 Broker 的报文上限同样必须配置。
2. 使用现有管理接口创建 `connectorType=MQTT` 的连接器，填写 endpoint、credentialRef 与上述 configJson。创建时默认停用。
3. 创建并启用外部设备绑定，维护内部设备编号、场景对象及点位映射。
4. 在受限环境文件中提供引用凭据，配置该工作进程的租户与连接器并启用 MQTT；数据库、Redis、Nacos 与 Kafka 沿用 IoT 服务原有配置。
5. 调用连接器现有 `/enable` 接口。正常检查周期为五秒，成功订阅后状态更新为 `CONNECTED`；停用接口仍使用原权限。配置异常或连接断开为未连接状态，并按退避重试。
6. 发布示例报文，核对 Inbox 记录、统一事件中的租户和绑定字段，以及三维投影查询。重复发布同一报文应保持同一事件编号，不能只用 MQTT 发送端“发送成功”证明业务链路完成。

首次接入时，Broker 拒绝订阅或将确认 QoS 降级为 0，均视为接入失败。用户名密码轮换后应重启该工作进程；相同 credentialRef 的环境值不会在长连接期间自动刷新。

## 实际依赖验收清单

真实环境仍需核验服务账号的主题权限、证书和主机名验证、Broker 持久存储、进程重启后未确认报文重投、双实例抢占、Redis 故障/租约过期、数据库不可用、连接器停用、毒消息阻塞处理和最终 Kafka/三维投影结果。跨地域 Redis 复制或主从切换可能改变租约可见性，不能将本租约当成数据库与 Broker 之间的严格分布式事务。
