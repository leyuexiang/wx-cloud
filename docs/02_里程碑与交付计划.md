# 里程碑与交付计划

版本：V1.2 评审稿。更新日期：2026-11-10。对应设计：[01 项目总体设计](01_项目总体设计.md)。对象存储分钟级执行计划见第 9 节，其余总体窗口继续保留原参考口径。

## 1. 计划口径与人员假设

以相对工作周 W1～W28 表达完整平台参考节奏。W1 从范围、人员和环境确认后的实际启动周起算，不按本文日期自动开工。该窗口是初步估算，不是已确认工期；M0 后按差异清单重估。

参考人员：两名后端、一名前端、一名 Unity/图形工程师、一名模型/物联集成工程师、一名测试工程师，共六名主要执行人员；架构、业务和运维按阶段参与。模型及物联默认由同一岗位先后承担，不同时排满两条主线。若人员、专项范围或外部依赖不同，调整窗口，不通过减少验收维持日期。

M2 交付首个编辑保存闭环，M3 完成完整二维、模板和发布，M4 接入 Unity 双端。后续行业领域不作为首批可用性的前置条件。

## 4. Unity 和行业专项工作包

### 4.1 M4：双端图形交付

核对 Unity 权威工程、实际版本、StartScene、构建参数和产物；冻结 Web/Windows 资源兼容矩阵。统一对象身份和场景代次，覆盖选中、变换、删除、清场、重载和主动事件。联调真实资源、地址续签、损坏包、缺依赖及权限拒绝。

信令/启动器能力确认后落地申请、续租和释放。两端分别记录画面、日志、资源占用和释放结果；一端成功不替代另一端，首帧不替代编辑交互。

### 4.2 M5：BIM 与模型数据

以 建筑模型及 RVT 验证专项为基础，让真实源文件经隔离工作进程产出可校验的几何、构件、属性、坐标和清单，再完成业务版本和场景绑定。重试不污染成功产物。模型容量、构件规模、首屏、解析成功率和精度分别测量，冻结样本及硬件后判定；RVT 由依赖支线落实。

### 4.3 M6：物联及数据通道

IoT API/BIZ 及三维状态投影源码已在 2026-11-04 合入 dev；后续核对其与实际服务器部署版本、数据库结构及维护归属的差异，不再将源码找回作为当前未解决前置。选择一种有真实设备/平台的协议，冻结身份、单位、事件时间、质量、幂等和回执。当前实现与验收程度统一见[IoT 专项进度](plan/02_IoT服务进度与后续计划.md#11-整体完成程度)。

遥测、业务接口拉取和媒体分开验收。媒体复用已有网关设计，接入新认证时核对用户及成功码检查；可播放不代表有设备控制权限。

2026-11-10 用户调整 IoT 专项近期顺序：先交付后端管理接口和网页管理端，作为既有管理能力的准备支线；范围为连接器、设备绑定及接收记录，复用认证/租户/权限。真实数据库、管理网关和字段迁移仍为交付前置，完整设备上行与三维画面不阻塞首批页面开发。此安排不把平台 M6 整体提前验收，安全凭据轮换及规则控制等保留后续出口，详细范围/依赖见[IoT 首批交付](plan/02_IoT服务进度与后续计划.md#41-首批交付后端接口与网页管理端)，状态只在专项台账维护。

### 4.4 M7：行业业务

先选一个可复现试点：设备温度异常 → 告警 → 人工确认 → 派单/审批 → 受控处置 → 回执关闭，再加入病害证据和构件绑定。告警、流程、命令各自维护权威状态，不直接改写其他领域表。

模型配准、图像定位和构件评级分别验证。缺少真值时可验收人工录入/复核，但不宣称自动定位精度达标。

复杂逻辑先失败用例再实现。关键安全、一致性及状态分支逐项覆盖；覆盖率不替代业务验收。模拟、真实接口、真实画面和现场测量分开记录，历史报告不抵扣新增能力验证。

每阶段须同时具备正常流程、拒绝路径、失败恢复、合同、部署回退和证据，才标为完成。代码完成但待真实联调或用户验证，登记为“待联调/待验收”，不能计入已交付能力。

## 7. 发布及变更治理

各里程碑形成可部署批次，登记源码/差异、前端与 Unity 构建、程序包摘要、迁移和配置版本。先隔离验证，再试点切换，观察指标后扩大。

迁移优先新增字段/表和兼容读写。程序包能回退不等于可删除已有新业务数据；优先前向修复。每批准备自己的回退方案，不重复借用“退回 metabase”的一次性部署脚本。

范围变化记录收益、合同/数据影响、测试和工期，由业务与技术负责人确定进入哪个批次。不能用新增功能挤占已冻结的安全、并发和恢复验收。

### 9.1 执行口径与环境门槛

每个叶子节点是一个 10～12 分钟的工作时间盒，包含读取本节点上下文、单个目标动作、对应检查和更新台账。默认单智能体顺序执行，不依据时间盒开启多智能体。实施节点须先有能复现边界的失败用例；表中的测试节点为后续最小实现提供约束，修复后运行适用回归。

时间盒到期而验收未过，保留原节点的进行中/受阻状态、记录实际耗时和检查点，并按 `原编号-R01/R02` 追加 10～12 分钟续做节点；不降低验收条件，不把故障修复及等待隐藏进“已完成”。新出现的大逻辑也按同样粒度拆分，原编号不重排。

长时间构建、上传、迁移、负载和人工验收采用“提交作业 → 有界观测 → 核验结果”。本表相应节点只承诺完成该次提交或观测；作业未完成则重复观测节点，不能为了满足 12 分钟强行终止数据复制或把替身当真实验证。等待时间单独记账。

| 门槛 | 实际需要的条件 | 不满足时允许继续的工作 |
| --- | --- | --- |
| 合同 | 权限、字段、错误、配额及场景上下文有冻结依据 | 继续设计/静态检查，不实现猜测的业务规则 |
| 真实依赖 | 独立 MySQL 库、私有 MinIO 桶、限定账户、空间与明确的测试数据边界 | 本地纯代码/替身检查；真实节点保持受阻 |
| Web | 当前消费者源码可用、适用规则及跨仓库修改属于实施授权 | 后端合同与候选检查；不声称浏览器闭环已完成 |
| 共享环境 | 核对当前会话对部署、迁移及对象删除的授权，备份及回退具体可审阅 | 完成候选包/脚本/预演，按缺失授权登记，不反复要求已给出的授权 |
| 历史迁移 | 来源、归属、规模和引用覆盖可核验 | 新文件试点可推进；未知来源不自动迁移 |

### 9.4 节点留证与里程碑关闭

每次记录：节点编号、开始/结束时间（Asia/Shanghai）、实际分钟、源码与工作区基线、修改文件、具体命令/作业号、期望与实际结果、证据路径、遗留项、下一节点。记录位置统一在 03，证据按对应实施批次保存到 `docs/evidence/`；不把秘密、完整签名或文件正文写进记录。

测试先失败后通过的节点分别保留两次结果；真实数据库/对象存储/浏览器与本地替身分栏。部署候选、实际部署、服务健康、真实业务和用户签收各自登记；有未验证关键出口时里程碑不得关闭。表中涉及多种故障场景的验收若不能在单时间盒完成，应追加同粒度节点逐个留证，不能只测正常路径就将整项关闭。

全专项结束至少具备：首期接口合同、增量迁移与数据保全证据、真实小文件闭环、固定发布引用和撤销、适用的大文件恢复、旧入口受管保护、回退后读取、历史数据差异报告。自动物理回收属于单独启用决策；条件未满足时可交付其受控工具和预演，但必须明确回收启用尚未交付。
