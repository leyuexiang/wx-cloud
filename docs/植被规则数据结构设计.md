# 植被规则数据结构设计

## 1. 结论

植被规则应采用“统一承载、分类建模”的结构：

- 所有规则统一存放在 `rules` 数组中，便于排序、快照冻结、版本管理和批量下发。
- 每条规则使用统一的公共字段，并通过 `type` 标识规则类型。
- 圈选、行道树、海拔分带的专属参数分别放入不同的 `config` 对象。
- 前端、Java 语言（Java）和 Python 语言（Python）均根据 `type` 选择对应的数据类型和校验逻辑。
- 不建议继续使用“一个对象包含所有类型字段、大部分字段为空”的扁平结构。

这种设计既保留统一接口，又能阻止无效字段组合。例如，行道树规则不能携带多边形孔洞，圈选规则不能携带道路种植侧。

## 2. 设计目标

1. 三类规则通过同一个任务接口提交。
2. 每类规则只包含自身有效的配置字段。
3. 规则快照可稳定序列化、计算摘要并进行幂等处理。
4. 支持多图层、物种资源版本和多边形孔洞。
5. 支持镜头视域（`camera-view`）冻结范围，生成过程不依赖前端实时镜头。
6. 支持后续增加新的规则类型，而不破坏现有规则结构。
7. 避免重复保存模型地址和版本，降低大规模规则快照体积。

## 3. 总体结构

```text
植被生成快照
├─ 场景、版本、随机种子和网格参数
├─ 高程数据源
├─ 正式生成范围
├─ 物种资源目录
└─ 规则数组
   ├─ 公共字段
   └─ 按规则类型区分的配置对象
      ├─ 圈选配置
      ├─ 行道树配置
      └─ 海拔分带配置
```

快照根对象建议如下：

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `sceneId` | 字符串 | 是 | 场景编号 |
| `ruleVersion` | 字符串 | 是 | 业务规则版本 |
| `generatorVersion` | 字符串 | 是 | Java 与 Python 共用的生成协议版本 |
| `seed` | 长整数 | 是 | 全局确定性随机种子 |
| `gridSizeM` | 数值 | 是 | 生成网格边长，单位为米 |
| `originLongitude` | 数值 | 是 | 网格原点经度 |
| `originLatitude` | 数值 | 是 | 网格原点纬度 |
| `elevationSource` | 对象 | 海拔规则必填 | 高程数据源及版本信息 |
| `generationRegion` | 对象 | 镜头视域规则必填 | 创建任务时冻结的正式生成范围 |
| `speciesResources` | 数组 | 是 | 去重后的物种模型资源目录 |
| `rules` | 数组 | 是 | 统一的植被规则集合 |
| `idempotencyKey` | 字符串 | 否 | 用户指定的幂等键；为空时由 Java 根据快照摘要生成 |

## 4. 规则公共字段

三类规则共用以下外层字段：

```json
{
  "ruleId": "rule-001",
  "type": "polygon",
  "layerId": "forest-layer",
  "seedOffset": 101,
  "config": {}
}
```

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `ruleId` | 字符串 | 是 | 快照内唯一的规则编号 |
| `type` | 枚举字符串 | 是 | `polygon`、`corridor` 或 `altitude-zonation` |
| `layerId` | 字符串 | 是 | 规则所属植被图层编号 |
| `seedOffset` | 整数 | 否 | 叠加到全局随机种子的规则偏移值 |
| `config` | 分类对象 | 是 | 由 `type` 决定的专属配置 |

`layerId` 只表示规则归属，不决定规则类型。同一个图层可以包含多条同类或不同类规则，但产品层如不允许混用，应由前端和 Java 业务校验明确限制。

## 5. 物种资源目录

模型地址和版本属于资源属性，不应在每条规则中重复。快照根对象统一保存资源，规则只引用 `speciesId`：

```json
{
  "speciesId": "species-camphor-001",
  "assetUrl": "https://assets.example.cn/vegetation/camphor.glb",
  "assetVersion": "model-v4",
  "minimumScale": 0.85,
  "maximumScale": 1.25
}
```

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `speciesId` | 字符串 | 全局唯一、非空 | 物种资源编号 |
| `assetUrl` | 字符串 | 非空、可访问 | 三维模型资源地址 |
| `assetVersion` | 字符串 | 非空 | 模型不可变版本 |
| `minimumScale` | 数值 | 大于零 | 默认最小缩放 |
| `maximumScale` | 数值 | 不小于最小缩放 | 默认最大缩放 |

规则中的物种混合项采用以下结构：

```json
{
  "speciesId": "species-camphor-001",
  "weight": 0.7
}
```

同一物种在不同规则中需要不同缩放范围时，可在混合项中增加 `minimumScale` 和 `maximumScale` 作为覆盖值；未填写时使用资源目录中的默认值。

## 6. 圈选规则

圈选规则类型为 `polygon`，配置包含外环、孔洞、分布方式、密度、株距、坡度和物种混合比例。

```json
{
  "ruleId": "polygon-rule-001",
  "type": "polygon",
  "layerId": "forest-layer",
  "seedOffset": 101,
  "config": {
    "polygon": [
      {"longitude": 120.1500, "latitude": 30.2500},
      {"longitude": 120.1550, "latitude": 30.2500},
      {"longitude": 120.1550, "latitude": 30.2550},
      {"longitude": 120.1500, "latitude": 30.2550},
      {"longitude": 120.1500, "latitude": 30.2500}
    ],
    "holes": [
      [
        {"longitude": 120.1515, "latitude": 30.2515},
        {"longitude": 120.1530, "latitude": 30.2515},
        {"longitude": 120.1530, "latitude": 30.2530},
        {"longitude": 120.1515, "latitude": 30.2530},
        {"longitude": 120.1515, "latitude": 30.2515}
      ]
    ],
    "distribution": "poisson",
    "densityPerHectare": 180.0,
    "minimumSpacingM": 4.5,
    "minimumSlopeDegrees": 0.0,
    "maximumSlopeDegrees": 35.0,
    "species": [
      {"speciesId": "species-camphor-001", "weight": 0.7},
      {"speciesId": "species-ginkgo-001", "weight": 0.3}
    ]
  }
}
```

校验要求：

- 外环和每个孔洞必须闭合，且至少包含三个不同顶点。
- 孔洞必须完全位于外环内部。
- 孔洞不能互相相交，也不能与外环相交。
- 有效面积等于外环面积减去全部孔洞面积，且必须大于零。
- `distribution` 仅允许 `poisson`、`grid`、`random`。
- 密度、株距和物种权重必须大于零。

## 7. 行道树规则

行道树规则类型为 `corridor`，配置包含道路路径、种植侧、道路偏移、株距和路径对齐方式。

```json
{
  "ruleId": "corridor-rule-001",
  "type": "corridor",
  "layerId": "roadside-layer",
  "seedOffset": 202,
  "config": {
    "path": [
      {"longitude": 120.1490, "latitude": 30.2495},
      {"longitude": 120.1525, "latitude": 30.2520},
      {"longitude": 120.1570, "latitude": 30.2560}
    ],
    "side": "both",
    "offsetM": 3.5,
    "spacingM": 8.0,
    "startOffsetM": 4.0,
    "endOffsetM": 4.0,
    "alignToPath": true,
    "species": [
      {"speciesId": "species-plane-001", "weight": 1.0}
    ]
  }
}
```

校验要求：

- 路径至少包含两个不同点，不能存在连续重复点或零长度线段。
- `side` 仅允许 `left`、`right`、`both`。
- 道路偏移、起始偏移和结束偏移不得小于零。
- 株距必须大于零。
- 物种必须存在于根对象的 `speciesResources` 中。

## 8. 海拔分带规则

海拔分带规则类型为 `altitude-zonation`。每个海拔带可使用不同的密度、株距、坡度和物种组合。

```json
{
  "ruleId": "altitude-rule-001",
  "type": "altitude-zonation",
  "layerId": "forest-layer",
  "seedOffset": 303,
  "config": {
    "scope": "camera-view",
    "gapPolicy": "reject",
    "zones": [
      {
        "zoneId": "low-zone",
        "minimumAltitudeM": 0.0,
        "maximumAltitudeM": 300.0,
        "minimumSlopeDegrees": 0.0,
        "maximumSlopeDegrees": 30.0,
        "densityPerHectare": 160.0,
        "minimumSpacingM": 5.0,
        "upperTransitionWidthM": 20.0,
        "species": [
          {"speciesId": "species-camphor-001", "weight": 1.0}
        ]
      },
      {
        "zoneId": "high-zone",
        "minimumAltitudeM": 300.0,
        "maximumAltitudeM": 1200.0,
        "minimumSlopeDegrees": 0.0,
        "maximumSlopeDegrees": 45.0,
        "densityPerHectare": 90.0,
        "minimumSpacingM": 7.0,
        "upperTransitionWidthM": 0.0,
        "species": [
          {"speciesId": "species-pine-001", "weight": 1.0}
        ]
      }
    ]
  }
}
```

校验要求：

- `scope` 仅允许 `polygon` 或 `camera-view`。
- `scope=polygon` 时，配置必须包含有效的 `polygon` 和可选的 `holes`。
- `scope=camera-view` 时，快照必须包含创建任务时冻结的 `generationRegion`。
- 分带必须按最低海拔升序排列，且不能重叠。
- `gapPolicy=reject` 时，相邻分带之间不能有海拔间隙。
- 最后一个分带的 `upperTransitionWidthM` 必须为零。
- 坡度范围必须处于 0 至 90 度，最低坡度不得大于最高坡度。
- 使用海拔规则时必须提供完整的 `elevationSource`。

## 9. 镜头视域冻结范围

`camera-view` 不是运行时读取浏览器镜头，而是创建任务时冻结的正式生成范围。推荐保存为闭合多边形：

```json
{
  "generationRegion": {
    "polygon": [
      {"longitude": 120.1480, "latitude": 30.2480},
      {"longitude": 120.1580, "latitude": 30.2480},
      {"longitude": 120.1580, "latitude": 30.2580},
      {"longitude": 120.1480, "latitude": 30.2580},
      {"longitude": 120.1480, "latitude": 30.2480}
    ]
  }
}
```

冻结后，该范围必须参与快照摘要计算。前端镜头后续变化不能改变已创建任务的生成范围。

## 10. 高程数据源

地理信息平台高程服务（ArcGIS）示例：

```json
{
  "elevationSource": {
    "url": "https://elevation.arcgis.com/arcgis/rest/services/WorldElevation/Terrain/ImageServer",
    "version": "world-elevation-2026-08",
    "verticalDatum": "EGM96"
  }
}
```

`url`、`version` 和 `verticalDatum` 必须共同参与快照摘要。只记录地址而不记录版本会导致同一快照在不同时间生成不同结果。

## 11. 三端类型设计

### 11.1 前端

前端建议使用带判别字段的联合类型（discriminated union）。`type` 决定 `config` 的具体类型，使错误字段组合在编译阶段即可被发现。

```ts
type VegetationRule =
  | RuleEnvelope<"polygon", PolygonRuleConfig>
  | RuleEnvelope<"corridor", CorridorRuleConfig>
  | RuleEnvelope<"altitude-zonation", AltitudeZonationRuleConfig>;
```

### 11.2 Java

Java 建议使用密封接口（sealed interface）和三个不可变记录类（record）。反序列化时以 `type` 作为子类型标识。

```java
public sealed interface VegetationRule
        permits PolygonRule, CorridorRule, AltitudeZonationRule {

    String ruleId();

    String layerId();

    Integer seedOffset();

    VegetationRuleType type();
}
```

实际实现时应为接口和每个字段补充与业务约束对应的中文注释，并配置杰克逊序列化组件（Jackson）的多态类型映射。

### 11.3 Python

Python 建议使用数据校验模型（Pydantic）的判别联合，以 `type` 自动选择对应配置模型。Python 仍需执行完整业务校验，不能只依赖 Java 的前置校验。

## 12. MySQL 表设计

### 12.1 设计结论

MySQL 数据库管理系统（MySQL）采用三张核心表：

```text
wx_veg_generation_task（生成任务）
├─ 1:N ─ wx_veg_generation_tile（地块结果）
└─ 1:0..N ─ wx_veg_publication（发布版本）
```

- `wx_veg_generation_task` 保存任务状态和创建任务时冻结的完整规则快照。
- `wx_veg_generation_tile` 保存 Python 按网格生成的地块结果。
- `wx_veg_publication` 保存可激活、回滚的稳定发布版本。
- 三类规则不分别建表，统一保存在 `snapshot_json.rules` 中。
- 场景、状态、版本和任务编号等高频查询条件独立成列并建立索引。
- 单株实例、候选点明细、三维模型文件和瓦片内容不进入 MySQL，只保存数量、摘要和文件地址。

当前项目的可执行建表脚本位于 `db/vegetation/vegetation.sql`。以下设计与该脚本保持一致。

### 12.2 生成任务表

`wx_veg_generation_task` 是任务状态的唯一事实来源。Java 必须先保存快照和本地任务，再调用 Python，避免进程在远端任务创建后、本地任务落库前退出而丢失任务索引。

```sql
CREATE TABLE IF NOT EXISTS `wx_veg_generation_task` (
  `id` bigint NOT NULL COMMENT '任务主键，由分布式编号生成器创建',
  `generator_task_id` varchar(128) DEFAULT NULL COMMENT 'Python生成器任务编号',
  `scene_id` varchar(64) NOT NULL COMMENT '场景编号',
  `snapshot_version` varchar(64) NOT NULL COMMENT '不可变规则快照版本',
  `rule_version` varchar(64) NOT NULL COMMENT '植被业务规则版本',
  `idempotency_key` varchar(128) NOT NULL COMMENT '任务幂等键',
  `status` varchar(32) NOT NULL COMMENT 'PENDING/RUNNING/SUCCESS/PARTIAL_FAILED/FAILED/CANCELED',
  `total_tile_count` int NOT NULL DEFAULT 0 COMMENT '总地块数量',
  `completed_tile_count` int NOT NULL DEFAULT 0 COMMENT '已完成地块数量',
  `failed_tile_count` int NOT NULL DEFAULT 0 COMMENT '失败地块数量',
  `candidate_count` bigint NOT NULL DEFAULT 0 COMMENT '候选点总数',
  `instance_count` bigint NOT NULL DEFAULT 0 COMMENT '最终实例总数',
  `generator_version` varchar(64) DEFAULT NULL COMMENT 'Python生成器及协议版本',
  `publication_version` varchar(64) DEFAULT NULL COMMENT '任务当前输出的发布版本',
  `manifest_url` varchar(512) DEFAULT NULL COMMENT '发布清单地址',
  `tileset_url` varchar(512) DEFAULT NULL COMMENT '三维瓦片清单地址',
  `source_hash` varchar(128) DEFAULT NULL COMMENT '规则快照和生成器源代码摘要',
  `snapshot_json` json NOT NULL COMMENT '创建任务时冻结的完整规则快照',
  `error_message` varchar(2000) DEFAULT NULL COMMENT '任务级错误信息',
  `creator` bigint DEFAULT NULL COMMENT '创建人编号',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `deleted` bit(1) NOT NULL DEFAULT b'0' COMMENT '逻辑删除标记',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_veg_task_idempotency` (`idempotency_key`),
  UNIQUE KEY `uk_veg_task_generator_id` (`generator_task_id`),
  KEY `idx_veg_task_scene_status` (`scene_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='植被生成任务';
```

关键约束：

- `id` 不使用自增，由项目现有分布式编号生成器创建，避免多实例写入冲突。
- `idempotency_key` 使用唯一索引，阻止网络重试或并发提交创建重复任务。
- `generator_task_id` 允许任务投递前为空，Python 返回任务编号后再更新。
- `snapshot_json` 是任务的不可变输入，任务创建后禁止修改。
- `snapshot_version` 表示输入快照版本；`source_hash` 表示快照与生成器源码的组合摘要，两者含义不能混用。
- 列表查询不得返回 `snapshot_json`，避免读取大字段造成无效的网络传输和内存占用。

### 12.3 地块结果表

地块表只保存可恢复的结果索引，不保存候选点数组或单株矩阵。每个任务内的 `tile_id` 必须稳定，重试同一地块时执行更新而不是新增记录。

```sql
CREATE TABLE IF NOT EXISTS `wx_veg_generation_tile` (
  `id` bigint NOT NULL COMMENT '地块结果主键，由分布式编号生成器创建',
  `task_id` bigint NOT NULL COMMENT '生成任务编号',
  `publication_version` varchar(64) NOT NULL COMMENT '地块所属发布版本',
  `tile_id` varchar(128) NOT NULL COMMENT '任务内稳定地块编号',
  `tile_row` int NOT NULL COMMENT '网格行号',
  `tile_column` int NOT NULL COMMENT '网格列号',
  `status` varchar(32) NOT NULL COMMENT 'PENDING/SUCCESS/FAILED',
  `candidate_count` int NOT NULL DEFAULT 0 COMMENT '地块候选点数量',
  `instance_count` int NOT NULL DEFAULT 0 COMMENT '地块最终实例数量',
  `content_url` varchar(512) DEFAULT NULL COMMENT '地块实例或瓦片文件地址',
  `content_hash` varchar(128) DEFAULT NULL COMMENT '地块内容摘要',
  `error_message` varchar(2000) DEFAULT NULL COMMENT '地块错误信息',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_veg_tile_task_tile` (`task_id`, `tile_id`),
  KEY `idx_veg_tile_publication` (`publication_version`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='植被生成地块结果';
```

关键约束：

- `task_id + tile_id` 唯一，保证 Python 重试上报时不会产生重复地块。
- 地块内容存放在对象存储或文件服务，MySQL 仅保存 `content_url` 和 `content_hash`。
- 批量上报地块时应使用批量插入或批量更新，禁止逐条查询后再逐条写入。
- 任务进度优先使用任务表的汇总字段读取，避免每次查询都扫描全部地块。

### 12.4 发布版本表

发布表只记录稳定输出引用。任务成功不等于自动激活，必须完成地块数量、文件可访问性和内容摘要校验后才能将发布状态改为 `STABLE`。

```sql
CREATE TABLE IF NOT EXISTS `wx_veg_publication` (
  `id` bigint NOT NULL COMMENT '发布版本主键，由分布式编号生成器创建',
  `scene_id` varchar(64) NOT NULL COMMENT '场景编号',
  `publication_version` varchar(64) NOT NULL COMMENT '场景内唯一发布版本',
  `task_id` bigint NOT NULL COMMENT '来源生成任务编号',
  `rule_version` varchar(64) NOT NULL COMMENT '植被业务规则版本',
  `generator_version` varchar(64) NOT NULL COMMENT 'Python生成器及协议版本',
  `manifest_url` varchar(512) NOT NULL COMMENT '发布清单地址',
  `tileset_url` varchar(512) DEFAULT NULL COMMENT '三维瓦片清单地址',
  `source_hash` varchar(128) NOT NULL COMMENT '规则快照和生成器源代码摘要',
  `status` varchar(32) NOT NULL COMMENT 'DRAFT/STABLE/ROLLED_BACK',
  `instance_count` bigint NOT NULL DEFAULT 0 COMMENT '发布实例总数',
  `tile_count` int NOT NULL DEFAULT 0 COMMENT '发布地块总数',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_veg_publication_version` (`scene_id`, `publication_version`),
  KEY `idx_veg_publication_scene_status` (`scene_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='植被发布版本';
```

关键约束：

- `scene_id + publication_version` 唯一，发布版本只需在场景内唯一。
- 同一场景原则上只能有一个 `STABLE` 版本。MySQL 无法用普通唯一索引直接约束带条件的唯一值，应在事务中锁定场景发布记录后完成状态切换。
- 回滚是将目标历史版本重新激活，并将当前稳定版本标记为 `ROLLED_BACK`，不得覆盖历史记录。
- 发布记录必须保存规则版本、生成器版本和源摘要，保证结果可追溯。

### 12.5 规则快照的存储方式

`snapshot_json` 保存第 3 节定义的完整根对象，其中包含 `speciesResources`、`rules`、高程数据源和镜头冻结范围。圈选、行道树、海拔分带不拆成独立关系表，原因如下：

1. 生成任务读取的是完整不可变快照，拆表会增加多表查询和重新组装成本。
2. 三类规则字段差异较大，强行统一关系表会产生大量空列。
3. 按类型拆表会提高快照版本恢复、摘要计算和协议升级的复杂度。
4. 规则生成时不会按单个字段进行数据库范围检索，没有必要为低频字段建立关系索引。

若后续确实需要按 `ruleId`、`layerId` 或 `type` 跨任务统计，可增加只读索引表或 MySQL 生成列，但完整快照仍是唯一事实来源，不能同时维护两套可写规则数据。

### 12.6 表关系与一致性

- `wx_veg_generation_tile.task_id` 逻辑关联 `wx_veg_generation_task.id`。
- `wx_veg_publication.task_id` 逻辑关联 `wx_veg_generation_task.id`。
- 当前脚本不建立物理外键，便于独立迁移、批量恢复和分库部署；Java 服务必须在写入地块或发布记录前校验任务存在。
- 任务采用逻辑删除。已有地块和发布版本的任务不能直接物理删除。
- 创建发布版本、切换稳定版本和回滚必须使用数据库事务。
- 任务状态更新应使用明确的状态条件，防止并发回调把终态覆盖回运行态。

### 12.7 查询与性能要求

- 任务列表使用 `idx_veg_task_scene_status`，并采用主键游标分页，避免大偏移量分页。
- 幂等创建直接查询 `uk_veg_task_idempotency`，不得先扫描同场景全部任务。
- 地块完成回调通过 `uk_veg_tile_task_tile` 定位记录。
- 发布列表通过 `idx_veg_publication_scene_status` 查询，不解析 `snapshot_json`。
- 大字段详情按需单独查询，任务列表、状态轮询和恢复扫描只读取必要列。
- 地块统计在写入时增量更新任务汇总字段，避免高频执行 `COUNT` 和 `SUM` 全表聚合。
- 模型地址、高程地址、模型版本和高程版本必须冻结在 `snapshot_json` 中，不能在生成过程中重新读取“最新配置”。
- 快照序列化前必须规范字段顺序和数值格式，保证 Java 与 Python 对相同数据计算出一致摘要。

## 13. 与当前 Java 实现的差异

当前 `VegetationGenerationRequest.VegetationRule` 是包含所有类型字段的扁平对象。迁移到本设计至少需要：

1. 将规则改为按 `type` 区分的三种具体类型。
2. 新增多边形孔洞字段 `holes`。
3. 新增物种模型版本字段 `assetVersion`。
4. 将物种资源提取到快照根对象的 `speciesResources`，规则通过编号引用。
5. 删除“海拔分带永远拒绝”的临时校验，但必须先确认 Python 已支持高程采样。
6. 增加外环、孔洞、分带连续性、资源引用和镜头冻结范围校验。
7. 提升 `generatorVersion`，避免旧版 Python 误解析新结构。
8. 同步更新前端类型、Java 数据传输对象、Python 数据模型和三端契约测试。

## 14. 兼容与迁移策略

建议采用协议版本整体升级，不在同一个版本内静默改变字段含义：

1. 保留旧协议 `0.1.0` 的读取能力，仅用于查询和重放历史快照。
2. 新结构使用新协议版本，例如 `0.2.0`。
3. Java 根据 `generatorVersion` 选择对应序列化和校验逻辑。
4. Python 在不支持协议版本时立即拒绝任务，并返回明确错误。
5. 前端只提交当前启用版本；历史任务详情按其原始版本展示。
6. Java 和 Python 上线新版本后，再开放海拔分带正式生成入口。

## 15. 最终约束

- 接口层统一：所有规则通过一个快照和一个 `rules` 数组传输。
- 类型层分类：三类规则必须使用不同的配置模型。
- 存储层统一：数据库保存完整不可变快照，不按规则类型拆分任务表。
- 校验层双重执行：Java 快速拒绝非法请求，Python 在生成前再次校验。
- 资源层去重：模型地址与版本统一登记，规则只保存引用和混合权重。

该结构适合当前三类植被规则，也为后续增加林缘、网格阵列或生态群落等规则保留清晰的扩展边界。
