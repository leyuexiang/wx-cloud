## 应用接入结果

三维服务增加遥测和定向分发的独立监听开关，默认继承原应用级监听开关。候选关闭历史监听，仅启动本批两种消费组，不增授旧业务主题权限。

使用实际租户 2、数据库、Redis 和模型修订验证：

1. 固定模型 `2117612791529533441` 修订 2，读取清单及 4 个文件，合计 15,056,120 字节，摘要及大小一致。
2. 草稿解绑后，固定发布的两个有效票据连接均收到同一 MQTT 状态事件。
3. 保持 WebSocket 订阅时重启 Kafka。服务恢复后继续接收消息，撤销一张票据后仅另一张有效票据收到后续事件。
4. 撤销发布后，最新遥测仍完成投影，发布连接不再收到事件。匿名、错误发布及未绑定实例均被拒绝。
5. 场景、连接器、设备绑定及票据样本通过业务接口清理，清理错误为空。

事件编号及检查结果见[真实链路报告](live-acceptance.json)。三维候选包 SHA-256 为 `958345f7a69db09271fe77545253b7cb14dec6f7045ad2fbd6895bbe93eb1363`。

## 停机消息恢复

使用修复后的物联网候选，在 Kafka 停机期间通过真实 MQTT 发送消息。观察到接收记录后暂停本批无持久化的测试 MQTT 代理，排除自动重新投递，专门验证人工重放。Kafka 停机期间接收记录先为 `CLAIMED`，发送超时后转为 `FAILED`，没有误记已发布。恢复 Kafka 后，授权重放事件 `3c9bdc7b-786f-3bd6-b4c4-428df3b197db`，记录转为 `PUBLISHED`，三维快照中事件编号和值一致。

测试 MQTT 代理恢复后，等待连接器结束退避并恢复连接再发消息。随后同一场景继续完成两票据实时推送、带订阅再次重启、撤销单张票据和撤销发布检查，全部通过，样本清理无错误。完整结果见[故障恢复报告](recovery-acceptance.json)。该验证不覆盖设备消息代理自身的持久化恢复。

## 本地验证

故障演练先发现实际部署的整数毫秒快照在重放时被当作秒，消息获 Kafka 确认但没有有效投影。两个新增回归在修复前均失败：一个错误解析到公元 58763 年，一个证明新快照没有使用标准时间字符串。修复后缓存独立的事件读写器，新快照保留纳秒并兼容旧毫秒/小数秒；不修改全局网页配置或历史业务数据，旧快照已丢失的精度不能恢复。

物联网模块发现 146 项测试，143 项通过，3 项因未配置 `IOT_MYSQL_TEST_URL` 跳过；失败和错误均为零，构建成功。物联网候选包 SHA-256 为 `b88a0c1a5f10f93be87dd159b93a6d71b7abac202f5f0ca382ada4be96a21c27`。
