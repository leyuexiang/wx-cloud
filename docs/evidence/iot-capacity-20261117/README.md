# IOT-M3-05 千设备容量基线与隔离容器恢复

2026-11-17，完成容量测量与容器恢复子项，**1000 台设备、每台 5 秒一条、50 人查看的目标未通过**。本批未修改或部署业务程序，后续须先优化有界持久接收，再按同条件复测。

## 测量边界

使用 148 真实认证、MySQL 接收记录、MQTT、Kafka、Redis 和 WebSocket。临时场景 `2122582759719366657`、1000 个独立设备绑定与二维消费实例，每个认证连接订阅全部选定设备。由一个模拟网关连接汇聚逻辑设备，50 条协议连接共用一个租户账号；没有测量 1000 条设备独立连接、50 个独立身份或浏览器/Unity 的渲染容量。

周期为每设备 5 秒，均匀发送，1000 设备对应 200 条/秒，50 客户端的理想扇出为 10000 次/秒。延迟为同一负载发生器从发送前到收到对应推送的单调时钟差，包含真实网络和后台处理，不受跨机时钟同步影响。按最接近秩法记录中位数、第 95 和第 99 百分位。报告只统计收到的推送，缺失样本独立计数，不能以这些分位数代替完整性结论。

工具 [`measure-capacity.py`](../../../tools/iot/measure-capacity.py) 使用标准输入接收秘密，配置和资源清单不含密码、令牌或私钥。最多 1000 设备、50 客户端、12 轮；每 20 个测点分批订阅，25 秒续租。积压超过 10 秒、客户端错误或发生器延迟超过 2 秒时停止新增发送，最多再观察 20 秒。当前工具新增 5 秒工程延迟门槛及失败退出码，正式业务延迟指标仍待签收。分批及分位数 3 项工具测试通过，语法检查通过。

## 瓶颈证据与解释

- 单客户端与 10 客户端对照均积压；采样时遥测 Kafka 消费组积压为 0～1 条，不能把当前现象全部归因为多人 WebSocket 扇出。
- MySQL 性能视图的累计摘要中，接收记录插入平均 **22.050 毫秒**（4975 次），发布结果更新平均 **19.346 毫秒**（4969 次）；设备查找平均约 0.142 毫秒。该汇总是截至取样时的累计值，不能当作本轮独立逐条计时或理论最大吞吐。
- 当前 `PahoIotMqttConnection.messageArrived` 串行调用持久接收，然后显式确认；接入的可靠性约束必须保留。结合单客户端对照和写入耗时，优先优化有界并发持久接收。正式根因修复效果仍需同条件复测，不能用扩大排队上限替代吞吐优化。
- 数据库 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1` 保持。未降低持久性、跳过鉴权或修改业务查询与发布实现。

停止压测并等待后台收敛后，三轮有效隔离容量测试的 **6508 条消息全部为 PUBLISHED**，无 FAILED/CLAIMED/DEAD_LETTER；恢复用例后合计 **6520 条 PUBLISHED**，见[最终接收记录汇总](inbox-final.json)。它证明最终持久接收与发布收敛，不代表 20 秒观察窗口内每个前端均收到全部实时推送。先前关闭的连接按既有快照补偿合同恢复。

容器资源原始采样见[原环境采样](system-samples.json)与[隔离环境采样](isolated-system-samples.json)；部分采样未包含后建的隔离接入实例，不能据这些 CPU 数据断言该实例没有压力。

## 隔离恢复实测

1. 在同一认证 WebSocket 上收到基线值。
2. 停止本轮隔离接入容器，发布 10 条 QoS 1 消息并取得 MQTT 代理确认，确认此时客户端未收到这 10 条。
3. 重启隔离 MQTT 代理，再启动同一个隔离接入容器，复用持久会话及原数据目录。
4. 约 **25.658 秒**后收到全部 10 条排队消息；继续发布一条新消息并回读 Redis 最新值 `100012`。

共收到 12 条唯一更新、0 重复，同一 WebSocket 保持，见[恢复报告](recovery.json)。这是有序容器重启及离线排队恢复；共享主机、常驻 MQTT/Kafka、数据库、Redis 和三维服务未重启，不能称为整机断电或备份还原验收。
