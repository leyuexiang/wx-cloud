# 工作站有界接收分进程与协议容量验收

2026-11-17，IOT-M3-05G。本轮交付可选的接收分进程工具，并完成当前工作站经正式入口的协议容量子项。历史高延迟的唯一原因尚未隔离，默认仍为原线程模式，50 个真实播放器不在本轮范围。

## 方案及修改

复用现有 `measure-capacity.py` 的身份登录、发布票据、MQTT 发送、订阅续租、逐条范围与序号校验、定长位图和直方图。新增同目录 `capacity_receivers.py`，命令增加 `--receiver-processes`：缺省 0 为原线程方式，1～5 将连接有界分配给独立接收进程，总连接数仍限 50。

父进程继续登录并按服务端编号去重，签发/撤销票据和注销身份；子进程只在内存中持有自己分配的令牌及票据。每进程复用原 `Viewer`，所有进程共同使用五个建连名额，不能借模式变更提高握手突发。发送仍独立运行，跨进程共享同一单调发送时钟，逐帧数据不经控制管道复制。每连接固定共享字节位图、60002 个直方图桶、计数和有界错误标志，只有所属接收线程写入，父进程只采样进度。

所有子进程确认 CPU 计时起点后才启动发布；统计分别保留父进程、发送进程、每个接收进程以及总 CPU。两种模式均计入排空阶段，历史旧报告未采用该 CPU 窗口时不能直接作成本对比。冻结并回收接收进程后才汇总，异常退出、缺少最终回执、准备失败和超时清理均不能通过。票据和身份仍由父进程统一回收。

不改变 1000 逻辑设备、每五秒一条、最多 50 连接/十分钟、五秒工程延迟门槛、两秒排程及十秒积压保护。使用方式与复制依赖见[工具说明](../../../tools/iot/README.md#可选接收分进程)，设计见[12.4](../../design/06_IoT定向WebSocket推送交付设计.md#124-有界接收分进程发生器iot-m3-05g)。

## 先失败再实现与检查

最初四项新增用例均因模块缺失失败，再完成共享统计、有限错误标志、分配及进程回收。实际准备夹具时发现外部目录使用 `spec` 动态导入原工具会受到新增顶层导入影响；此时尚未创建设备夹具或发送遥测。改为仅在选择分进程时延迟加载，并补独立进程从外部目录导入的回归。

真实小样本使用两个独立接收进程、两个查看账号，20 条上报/40 次推送完整，P95 612 毫秒，零进程错误，票据及登录会话各两条已回收，见[小样本报告](process-smoke.json)。该轮发送速率仅每秒两条，不冒充目标容量。

最终新增的两个故障断言先复现：接收进程未确认计时或发送进程启动失败时，两端控制管道未关闭。随后将责任范围提前到计时确认之前，尚未启动的发送进程不做 `join`，两端管道仍关闭，票据回收不变。最终 **23 项工具测试全部通过**，包含真实跨进程缓冲、重复与分位保守取整、未知错误信息有界化、准备/运行异常退出、缺回执、超时回收、全局建连名额，以及准备失败时票据和会话清理。

此次只改容量工具及文档，没有 Java/Web/Unity 业务源码、业务部署或结构迁移。[部署摘要](deployment-health.json)仍为后端 `40d40eff`、网页 `b3711dd`，常驻配置与回退不变。本轮未调用浏览器或 Unity 联调，上一轮页面结果未重复计入本轮通过。

## 身份与同路径交替短测

新建独立临时租户、套餐和 50 个只读账号，复用正式管理接口准备。用户名从一开始符合登录长度，角色仅有查询/订阅以及无动作祖先菜单。[逐身份核对](identity-checks.json)确认 50 个服务端编号唯一、权限准确；用户列表和场景写入被拒绝。原租户 2 的权限及配置没有修改。

所有对照都来自当前工作站，使用同一 HTTPS 正式 `/dimensions/ws/iot-state`、同一个固定发布夹具、1000 逻辑设备、50 个独立账号、每条连接订阅全部 1000 点位，周期均为五秒。按线程 A、五进程 A、线程 B、五进程 B 顺序交替，每轮发送 2000 条，完整收到 100000 次推送，零重复错误且票据/会话全部回收。

## 版本和验证边界

[实际运行源码摘要](run-source.json)固定十分钟使用的工具文件。短轮之后只增加逐进程 CPU 列表及准备失败的单元测试，接收/校验路径相同。十分钟结束后又修正上述启动前失败的管道清理责任范围，未改变正常发布及接收语义；最终源码摘要在[检查汇总](checks.json)，最终 23 项回归通过，但没有将这个故障分支修复后的文件写成重新执行过十分钟容量。

协议结果是本轮实测；历史首次高延迟根因未被证明，前两轮同一路径的自然波动也已保留。可选分进程发生器已提供一条通过的工作站容量路径，不应据此更改业务服务线程、授权或扩大服务队列。

## 对账与清理

[接收对账](inbox-final.json)累计 **128020 条全部 `PUBLISHED`**，与小样本、四个短轮和十分钟的实际确认一致。临时固定发布 **252 张容量票据全部撤销**；权限边界原发布的另一张票据单独回收。[最终审计](final-audit.json)确认临时发布撤销、活动用户和访问令牌均为零。

[数据清理](cleanup.json)回收 1000 个绑定、临时场景及连接器。[身份清理](identity-cleanup.json)回收 50 查看用户、工作管理员、查看角色、临时租户/套餐和七个权限菜单，原租户配置及既有角色授权前后对照一致。受保护自动角色保留，指向已删除菜单的一条关联作为审计保留，有效权限为零。既有自删管理员退出日志再次返回业务码 400；令牌实际已清空，不把该错误计作退出成功，也没有直接改库绕过保护。

[主机回收](host-cleanup.json)移除两个临时容器、受限身份材料、证书副本、工具目录及本轮负载目录。本机 18885 转发核对进程后停止；原 18884、常驻 MQTT、业务服务和回退保留。[原场景核对](original-scene-check.json)保持三个场景及固定发布修订 5。

本轮沿用之前被策略拦截清理的 D 盘 Python 缓存，不再次尝试删除，不加入提交。构建、测试日志、缓存及报告都留在 D 盘。原 Unity 工作区既有删除状态和前端声明文件换行偏好未改。
